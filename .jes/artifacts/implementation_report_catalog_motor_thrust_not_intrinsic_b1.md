## Files changed

- `src/jarvis/core/component_writers.py` — **N1 (durability)**: in `set_motor_component`'s exact/fallback OP mirror block, the `PropertyValue` written to `spec.properties["thrust_n"]` now carries `source="calculated"` instead of `source="declared"`. This is the exact G5-precedented gate: `component_resolver.resolve_propulsion_parameters` only treats a `properties["thrust_n"]` value as the resolvable magnitude when its `source == "declared"` — tagging the OP-derived mirror `"calculated"` (the number the user never typed; the system derived it) makes the resolver skip re-deriving `per_motor_max_thrust_n` from it on a later, unrelated recalculation, so `current_parameters["per_motor_max_thrust_n"]` (written unconditionally by `set_motor_component` on every call) survives instead of being silently reverted. No other line in this function changed — `legacy_estimate`/unbound branches are untouched, still `source="declared"` from `bind_motor_from_catalog`, exactly as before.
- `src/jarvis/core/motor_catalog_assist.py` — **§3.3 (CLI copy hygiene)**: `_format_candidate_line` and `format_motor_chosen_line` each gained a trailing honesty marker (`" (pico catálogo)"` / `" (pico catálogo, se refina con hélice/batería)"`) appended **after** the existing formatted body, never inside it — every existing exact-substring test assertion (`"1. demo_motor  →  12.0N, 55.0g, 900KV, ~280W" in full`, `"10.042" in msg`, etc.) still holds because the marker is a pure suffix. Both functions had no access to `project_state`/a resolved `propulsion_resolution` at their call sites without a signature change (out of this IC's minimal scope, per its own "implementer choice within honesty" note) — the static marker names the figure as a catalog peak without inventing a propeller/voltage condition that isn't known at that point in the flow.
- `src/jarvis/core/project_closure.py` — **§3.4 (BOM tail, implemented, not deferred)**: `_bom_completeness_tail` gained a `motors`-keyed branch, reading the already-computed `current_parameters["propulsion_resolution"]` JSON (written by `set_motor_component`; read only, never re-derived) to append an honest tail when the shown thrust is **not** specific to the actually-bound propeller/voltage: `"{completeness} — pico de catálogo, sin operating point"` for `legacy_estimate`, `"{completeness} — operating point fallback, no específico de esta hélice"` for `fallback_operating_point`. `exact_operating_point` keeps the plain `(completeness)` tail — nothing to disclose, the shown number already is the bound-hardware-specific figure. This follows the exact same pattern as the pre-existing `flight_controller`/`frame` branches in the same function — purely additive text, zero change to `classify_component`/`_measurable_and_missing_fields`/the `defined`/`declarative` bucket routing (which stays untouched, since threading resolution-awareness into that shared, architecture-progress-linked function would have been the "wide BOM redesign" the IC told me to avoid).
- `tests/test_phase2_lookup_operating_point.py` — 3 new tests: the required regression (exact-OP mirror tagged `calculated`, survives a simulated `resolve_propulsion_parameters` + `apply_to` recalculation at `13.4841`, not reverted to `10.042`), a companion proving the `fallback_operating_point` branch is also tagged `calculated` (even though its value numerically coincides with the bare catalog peak), and a companion proving `legacy_estimate` is unaffected — its `properties["thrust_n"]` stays `source="declared"`, unchanged.
- `tests/test_assisted_acquisition.py` — extended two existing tests (`test_format_candidate_line_detailed_and_quick_forms`, `test_catalog_pick_verified_motor_without_nominal_watts_does_not_crash`) with assertions that the new honesty markers are present, rather than adding near-duplicate tests.
- `tests/test_project_closure_v1.py` — 3 new tests covering the three `_bom_completeness_tail` motors branches: `legacy_estimate` gets the catalog-peak tail, `fallback_operating_point` gets the not-propeller-specific tail, `exact_operating_point` keeps the plain `(completeness)` tail (a regression guard proving the new branch doesn't leak into the case that shouldn't show it).

## Behavior changed

- A catalog-bound motor whose thrust resolves to a real `exact_operating_point`/`fallback_operating_point` (currently possible for `emax_rs2205s_2300` and `sunnysky_r2205_2500` only, per the investigation's seed inventory) now has that resolution **durable** across any later, unrelated physical recalculation (`iterate.py`, `param_definition_session.py`'s wizard continuations) — previously, the mechanism existed for this value to be silently reverted to the bare catalog peak the moment any such recalculation ran without also re-invoking `set_motor_component` (the investigation's empirical proof: `resolve_operating_point(...) → 13.4841` immediately clobbered back to `10.042` by `resolve_propulsion_parameters` + `apply_to` when the mirrored property was tagged `"declared"`). Numerically, this changes nothing for any of today's 20/22 motor rows with no `operating_points[]` data at all, and nothing for `emax_rs2205s_2300`'s `fallback_operating_point` case specifically (its mirrored value was already numerically identical to the bare peak, by the seed's own deliberate "★-locked regression contract" construction) — the fix is a correctness hardening for the one live case that can actually diverge (`emax_rs2205s_2300` bound with a real propeller/voltage matching its `exact_operating_point` row) and for any future seed row where richer `operating_points[]` data is added.
- CLI candidate lines (`_format_candidate_line`, used by every catalog-listing/quick-menu surface via the existing FN-006 single-source pattern) and the "Motor elegido" confirmation line now name the shown thrust as a catalog peak rather than presenting it as a bare motor fact.
- BOM output for a `motors` entry in the `defined` bucket now discloses, when applicable, that the shown thrust came from `legacy_estimate` (no operating-point data exists for this motor at all) or `fallback_operating_point` (a real but self-reported not-propeller-specific figure) — `exact_operating_point` entries are unaffected, matching every other `defined` component's plain tail.
- No change to `resolve_operating_point`'s ladder/matching logic, to `MotorSpec.thrust_n`'s required-ness, to any seed JSON number, to `find_motors_for_requirements`/`_motor_covers_requirements`'s design-space ranking/filtering (both still read `MotorSpec.thrust_n` directly, unaffected by anything this IC touches), or to `classify_component`'s `defined`/`declarative` bucket routing.

## Remaining risk / notes for review

- The CLI honesty markers are static strings (`"(pico catálogo)"` / `"(pico catálogo, se refina con hélice/batería)"`) rather than resolution-aware text, because `_format_candidate_line`/`format_motor_chosen_line` operate on a bare `MotorSuggestion` dict with no `project_state`/`propulsion_resolution` access at their call sites. This satisfies the IC's own "or" clause (static marker acceptable; do not invent an unknown condition) but means a chosen-line shown *after* an exact-OP resolution still says "pico catálogo" rather than naming the real resolved condition — a genuine, but explicitly out-of-scope-for-B1, follow-on if the Engineer later wants the "show the resolved figure instead" branch of §3.3's table.
- The BOM tail's `legacy_estimate`/`fallback_operating_point` wording is a first pass at honest phrasing (matching the investigation's own §D phrase-matrix illustration), not a locked copy deck — easy to revise in a future cycle without touching the underlying `propulsion_resolution` read.
- As noted above, this fix is currently observable for exactly one seed pairing (`emax_rs2205s_2300` + a propeller/voltage matching its `exact_operating_point` row); it is a correctness hardening against a proven mechanism, not a fix for a symptom any shipped UI flow was already exhibiting today (per the investigation's own honest framing of what was empirically demonstrated vs. what is latent).
