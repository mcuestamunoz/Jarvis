- `src/jarvis/core/declared_box_pose_declare_assist.py` (**new**) — pure parser exactly per §3.1–3.3. `PoseDeclareResult` (`SET`/`CLEAR`/`AMBIGUOUS_ORIGIN`/`INCOMPLETE`/`NONE`). SET gate requires **all three** of `declara(r)`, `\bmm\b`, `respecto` (never `fija`, confirmed absent from every regex in this file). CLEAR gate is `quita(r) (la) pose` — confirmed via test that it does **not** match `"quita el montaje del esc"`. Subject segment is the text before the first `respecto`; origin segment is the text after it — both resolved via the two new public wrappers, never a re-implementation. Axis extraction (`_AXIS_MM_RE`) matches every `N mm en <axis>` occurrence in the subject segment via `finditer`, mapping `x`/`largo→x_mm`, `y`/`ancho→y_mm`, `z`/`alto→z_mm` — a closed alternation, so a directional word like `adelante` can never match the axis-token group at all (confirmed by a dedicated test: `"declara el esc a 5 mm en adelante respecto al fc"` finds zero axes and returns `INCOMPLETE`, not a match). Later repeated axis tokens overwrite earlier ones in the same phrase (dict assignment order). The parser never checks `_geometry_from_spec` itself — origin box-ness is left entirely to the writer, confirmed by a dedicated test that a shapeless origin (`frame_plate`) still parses to `SET` at this layer.
- `src/jarvis/core/orchestrator.py` — **§3.5**: new `_try_handle_declared_box_pose(self, user_input)`, placed directly after `_try_handle_catalog_refresh` (same file region, same pattern as every prior deterministic IDLE bridge this session), and dispatched in `_handle_user_text_inner` immediately after the catalog-refresh bridge and **before** FN-005's help-choose chain — confirmed via `grep` that this places it before FN-014's own dispatch call site too, satisfying the locked ordering (`mounted_on → refresh → pose → FN-005 → FN-014`). Behavior exactly as locked: `NONE` → falls through unchanged; `INCOMPLETE` → an interactive prompt naming what's missing; `AMBIGUOUS_ORIGIN` → candidate list (non-empty) or an honest "not found" message (empty candidates); subject not yet declared → honest error, writer never called; `ValueError` from the writer (non-box/self/missing origin) → surfaced verbatim; `SET`/`CLEAR` → calls `set_component_declared_box_pose` exactly as-is (no forked copy — confirmed via `git diff --stat` showing zero lines changed in `component_writers.py` this cycle), saves state, and returns a confirmation whose second line is `f"Ejes: {POSE_AXES_HONESTY_LABEL}."` — the constant imported from `spatial_board`, never a paraphrase.

## Note on T11's exact shape (deviation from the IC's literal test description, reasoned through)

The IC's own T11 wording ("declarar el esc" still acquisition-shaped) implicitly assumes FN-014's acquisition flow would catch this phrase. Testing it end-to-end via `handle_user_text` with the IC's own `_RefuseLLM` fixture (which asserts the LLM is never called) revealed that this specific phrase — with `esc` already `completeness="high"` in the test fixture — falls through **all** deterministic routing (including FN-014, which has nothing to offer for an already-fully-declared component) and reaches the LLM, exactly as it would have **before** this IC existed (confirmed: this IC's own dispatch correctly returns `None` for this phrase, proven directly).
