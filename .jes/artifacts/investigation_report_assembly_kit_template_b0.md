## Baseline inventory (live tree, cited)

- **`SYSTEM_ARCHITECTURES["dron"]`** (`system_architecture_catalog.py`): 4 blocks — `propulsion`, `energy`, `structure`, `control`. **`BLOCK_TO_COMPONENTS`** expands these to exactly 7 unique component keys: `motors`, `propellers`, `esc` (propulsion); `battery`, `motors` (energy — `motors` intentionally shared, per the file's own "DA-MOTORS" comment); `frame` (structure); `flight_controller`, `sensors` (control). This is the complete "template" a novice is offered — confirmed by reading the dict directly, not assumed.
- **Board slot emission** (`spatial_board.py`, `_expected_keys_by_column`): a key named in a **declared** block's `BLOCK_TO_COMPONENTS` list that is absent from `components` becomes a `kind: "slot"` node ("estado: no declarado"). A key that isn't in `BLOCK_TO_COMPONENTS` at all (an adapter, a connector, wiring) **cannot become a slot** — the mechanism only iterates the 7-key set, so such an item is not "pending," it is architecturally invisible.
- **`build_component_bom`** (`project_closure.py:559`): `expected_keys` is derived the same way (declared `system_blocks` → `BLOCK_TO_COMPONENTS`, deduped). A key in `expected_keys` absent from `components` becomes `"missing"` — the BOM's own not-yet-acquired bucket. A component present but not in `expected_keys` (an "extra" the user or a writer added) is still classified via `classify_component` into `defined`/`incomplete`/`declarative` — the BOM **can** show extra components, but nothing today prompts a novice to add one, because no acquisition/Continuity path knows such a category exists.
- **Structure B children already exist and already work**: `frame_part_specs_from_catalog` (`catalog_bind.py:389`) projects a bound frame's curated `arm_count`/`plates[]`/`cage_material`/`standoff_material` fields into child `ComponentSpec`s with `parent_key="frame"` (`structure_part`, keys `frame_arm`/`frame_plate[_N]`/`frame_cage`/`frame_standoff`, capped at `FRAME_PLATE_MAX_SIBLINGS = 8`). **These children are already excluded from top-level BOM classification** (`project_closure.py`'s own comment: "a declared frame part... is display-only under its parent... never a top-level BOM peer") — meaning this mechanism has **zero effect on architecture/BOM PASS** today, which is exactly the property Locked Stance #6 requires of anything new.
- **Live demo, read directly**: `system_blocks: ["propulsion", "energy", "structure", "control"]`; declared component keys: `battery`, `esc`, `flight_controller`, `frame`, `frame_arm`, `frame_cage`, `frame_plate`, `frame_plate_2`, `frame_plate_3`, `frame_plate_4`, `frame_standoff`, `motors`, `propellers`, `sensors` — all 7 template keys present, plus 6 frame children already generated by the existing Structure B mechanism from the bound `armattan_rooster_5in` catalog row. **Nothing** resembling a prop adapter, a power connector, or a signal harness appears anywhere — not as a component, not as a slot, not as a BOM entry. A novice opening this exact project sees a "complete" 4-block quad with a frame hardware breakdown and no signal that anything else is needed to actually assemble it.
- **Project-create / architecture session** (`system_definition_session.py:99`): for a known `vehicle_type`, the session proposes the domain's fixed block list up front (`get_domain_architecture`) — the user is asked to confirm/adjust **blocks**, which is what fixes the 7-key set for the rest of the project's life (short of a later `system_blocks` edit).

## A. Two products

**P-energy** (what exists today, and what must never be silently widened per Locked Stance #6): the deterministic feasibility/readiness chain — `propulsion`/`energy` composite-block completion (AND-strict: params **and** components), `resolve_operating_point`, autonomy/hover calculations, Structure/Propulsion PASS. This is computed from exactly the 7 template keys' `properties`/`current_parameters` and must keep working unchanged no matter what template growth happens elsewhere.

**P-kit** (what a novice cannot see today, and what this investigation is about): "what do I physically need in my hands to bolt this together." Today Jarvis silently equates "P-energy architecture complete" with "ready to build," which is false — a novice with `motors`+`propellers`+`esc`+`battery`+`frame`+`flight_controller`+`sensors` all `completeness: high` still cannot mount a propeller without a shaft adapter (if the bore doesn't match), cannot power the ESC without a battery connector, and cannot wire signal without a harness — **none of these are represented anywhere**: not a component, not a slot, not a BOM line, not a Continuity prompt. The gap is not "these items are pending" (which the system already knows how to say) — it's "these items don't exist as a category the system can even ask about."

## B. Candidate Buys (ranked)

| ID | Shape | Assessment |
|---|---|---|
| **B0** | Keep 4-block / 7 keys; kit is a later product | Safest, zero risk, but does not address the Engineer's actual ask — a novice still sees no signal that a kit gap exists at all. Pure status quo. |
| **B1** | Add a small named pending set to `dron` (physical entities, cap N≤8) | **Directly addresses the ask**, but carries a real architectural risk not mentioned in the IC's own framing: `BLOCK_TO_COMPONENTS["propulsion"]`/`["energy"]` are the exact lists that drive AND-strict composite completion (`get_block_type`). Naively appending new keys to those lists would make propulsion/energy PASS require them too — a direct violation of Locked Stance #6 ("must remain computable... do not silently widen PASS"). The correct shape is **not** "add keys to the existing propulsion/energy lists" but either (a) a new, non-"composite" architecture block whose keys are display/BOM-only and never gate PASS (the existing `actuation` block is precedent: `BLOCK_TYPE["actuation"] = "param"` and `_block_progress_status` already ignores its `component_keys` for completion purposes — the same trick could apply to a new `assembly_hardware`-style block), or (b) a pending mechanism that is visible on the Board/BOM without going through `BLOCK_TO_COMPONENTS`'s completion role at all. **This design question is the central thing the next IC must resolve** — it is not free to just add three lines to the existing dict. |
| **B2** | Bound-frame Included → extra BOM children under `frame` (pending if not in seed) | **Already implemented as a mechanism** (`frame_part_specs_from_catalog`, confirmed above) and already has zero PASS impact (children are `parent_key`-excluded from top-level classification). The only real gap is catalog **seed richness**: the parent Plate L×W investigation already found GetFPV's fuller Rooster kit list names two plates (`HD [Camera/Cage] plate`, `Rear VTX plates`) not yet in the curated `plates[]` array for `armattan_rooster_5in` — seeding those would surface more real children with **no new subsystem, no PASS risk, no schema change**. This only helps once a frame is actually bound to a catalog SKU with a rich-enough seed, and it does not cover non-frame accessories (a battery connector, an ESC-to-FC harness) — those have no analogous "parent" component type today. |
| **B3** | Doc-only: Continuity sentence "this architecture is not a full kit" | Trivially safe, zero schema risk, but purely expectation-management — it does not give the novice anything actionable ("what do I still need") beyond a disclaimer. Cheapest possible honesty patch, weakest capability gain. |

**A 40-line FPV shopping list is explicitly rejected** — it would violate Locked Stance #1 (blocks as functional views, not ownership) by turning the catalog into a commercial BOM engine, and Locked Stance #3 by pressuring invented SKUs to fill every line.

**Default lean: B1, narrowly scoped (recommend N≤4, not the full cap of 8), built as a non-PASS-gating addition** — this is the only candidate that actually gives a novice a **named, physical-entity "you still need this"** signal for items no existing mechanism can represent. Candidate physical entities (each cited as load-bearing for the literal "montar" step, not a verb/service):

| Candidate key | Why load-bearing for assembly |
|---|---|
| `power_connector` | The battery cannot deliver power to the ESC without one (e.g. an XT60/XT30-class connector/pigtail) — every quad needs exactly one, independent of which battery/ESC SKUs are bound |
| `signal_harness` | The flight controller cannot command the ESC without a signal path when FC and ESC are separate physical boards (the common case in this catalog today — no "AIO stack" SKU exists) |
| `prop_adapter` | Only conditionally needed (some motor-shaft/prop-bore pairs mount directly), but when needed it is a hard blocker for the one physical action ("mount the propeller") this whole system exists to support — proposed as a **conditionally-pending** slot, not a universal one, to avoid a false-positive "you're missing this" for builds that don't need it |

Recommend **not** including generic mounting hardware (screws/standoffs) as a fourth key this round — those are already partially visible via the existing `frame_standoff` Structure B child and the frame's own bolt-count text (per the Plate L×W investigation's kit-list findings); a dedicated key would duplicate an already-working path (B2), not fill a genuine gap.

## C. Acquisition — "ask as you go" using existing machinery only

No new dialogue subsystem is needed or proposed:

- A new pending key (if B1 is later approved) becomes a **slot** on the Board exactly like today's 7 keys — same `kind: "slot"`, same "estado: no declarado" text, same code path in `_expected_keys_by_column`/`project_spatial_nodes`. Zero new UI.
- The same key becomes a **BOM `missing` entry** via `build_component_bom`'s existing `expected_keys` walk — zero new BOM code, provided the key is reachable from a `system_blocks` member (which is exactly why B1's block-placement question in §B matters: it must be reachable for slot/BOM visibility while *not* being reachable for AND-strict completion — two different consumers of the same `BLOCK_TO_COMPONENTS` structure that currently cannot be told apart without a new distinction like the existing `param`-type/completion-ignoring precedent).
- **Unknown stays unknown, never guessed**: exactly as today's `frame` slot never proposes a SKU, a `power_connector` slot would never propose "XT60" or any part number — DEFINE_MISSING/Continuity's existing "declare what you have, or leave it pending" pattern applies unchanged. This satisfies Locked Stance #3 by construction, not by new validation code.
- **No Conversation Engine, no LLM shopping list**: the acquisition surface stays the same deterministic IDLE/DEFINE_MISSING/catalog-assist chain already used for the 7 existing keys — a new key is data (one more `BLOCK_TO_COMPONENTS` entry, correctly scoped per §B), not new logic.

## Summary: what stays P-energy vs what would be P-kit

**Stays P-energy, untouched by any candidate Buy**: `propulsion`/`energy` AND-strict composite completion, `resolve_operating_point`, autonomy/hover math, Structure/Propulsion PASS — all computed from the existing 7 keys' `properties`/`current_parameters` only. B1's central design constraint (§B) exists specifically to guarantee this stays true.

**Would become P-kit** (novice-facing "can I actually assemble this" signal, not a feasibility number): a small, capped (`N≤4`), physical-entity pending set (`power_connector`, `signal_harness`, `prop_adapter`) surfaced via the existing slot/BOM "missing" machinery, plus (independently, lower-risk, already-mechanism-complete) richer frame-kit seeding via B2 for already-bound frames. No shopping list, no invented millimetres, no new subsystem.
