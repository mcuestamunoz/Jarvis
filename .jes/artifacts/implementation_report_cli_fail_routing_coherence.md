## Files changed

- `src/jarvis/core/project_closure.py` — two new pure functions: `frame_next_missing_datum(project_state)` (returns `"mass" | "material" | "size_class" | "class_incompatible" | None`, composing persisted `components["frame"].properties` with the existing `frame_class_compatibility_state`, never re-deriving `_frame_completeness`) and `frame_next_missing_question(project_state)` (locked copy per datum — the size-class sentence is verbatim from §2.1; mass/material reuses the existing Structure A three-part/two-part examples; class-incompatible is new, LEVEL-A-worded, consistent with Structure A's existing "no cabe/no verificado" vocabulary).
- `src/jarvis/core/acquisition_brief.py` — `build_acquisition_brief` now asks `frame_next_missing_question` for `key=="frame"` when a project is available, falling back to the static `COMPONENT_PROMPTS["frame"]` when the helper returns nothing (frame complete) or no project exists.
- `src/jarvis/core/orchestrator.py`:
  - `_component_prompt_for_first_missing` — replaced its own inline "mention pulgadas when D known" check with a call to `frame_next_missing_question`, so it and Acquisition Brief share the exact same copy.
  - `_handle_component_description`'s freeform-save `still_missing` computation — a `"high"`-completeness frame now still counts as missing when `frame_next_missing_datum` is non-`None` (§2.2), so the wizard doesn't close on a class gap.
  - The "low-completeness" frame probe (the branch handling e.g. `"ayúdame a elegir"` after a frame was already saved) — now merges the *persisted* frame's properties with whatever this turn's (usually uninformative) utterance parsed, via a lightweight `SimpleNamespace` shim, before asking the shared helper — fixes the exact walk bug (deciding from `spec.properties` of the current utterance alone re-asked for mass/material that were already known).
  - `build_startup_context`'s architecture in-progress branch (`"structure"`, non-composite type) — now asks `frame_next_missing_question` first, falling back to the generic "define los parámetros que faltan" only when the helper has nothing to say.
  - `build_startup_context`'s architecture-complete branch — no longer sets `proactive_question` to the "puedes optimizar o simular" sentence when the last simulation's `status` isn't in `("pass","","ok")` or `can_fly is False`.
  - `_append_arch_progress_hint` — same `_sim_is_failing` check added; on a real simulation failure it now appends only `"✓ Arquitectura completa ({progress})."` (no "puedes optimizar o simular" suffix), keeping the evidence line `test_fn021_session_hygiene.py` asserts on while dropping the non-action.
- `src/jarvis/core/project_continuity.py` — rank-2 (`status_type=="warning"` or raw `sim_status not in ("pass","","ok")`) restructured into 4 sub-branches after `_underspec_live` (unchanged, still first): (2) `_autonomy_calculated_below_target` **and** `can_fly is True` → existing `_AUTONOMY_BELOW_NEXT_STEP` verbatim; (3) same autonomy condition but `can_fly` not `True` → new `_THRUST_FAIL_AUTONOMY_BELOW_NEXT_STEP` (names both problems, never claims PASS); (4) `can_fly is not True` alone → new `_THRUST_FAIL_NEXT_STEP`; (5) existing generic fallback, now skipping `proactive_question` when it contains `"puedes optimizar o simular"` (falls back to the original "Corrige la causa..." string instead of echoing a non-action).
- `src/jarvis/adapters/cli/main.py` — `render_startup_context`'s `status_type=="warning"` branch now gated on `not continuity.get("situation")`, matching its `nominal`/`no_data` siblings — Continuity's own honest `"fail"` situation line no longer gets contradicted by a hardcoded `"WARNING"` line directly below it.
- `tests/test_cli_fail_routing_coherence.py` — new, 7 tests (see below).
- `tests/test_project_continuity.py` — one pre-existing test (`test_continuity_sim_fail_without_underspec_unchanged`, from the T1 catalog-assist IC) had a simulation fixture that never set `can_fly` at all — every real `FeasibilitySimulator` result always sets this field, so the fixture was incomplete. Added `"can_fly": True` explicitly (the value every other test/production caller in the file already sets for a "thrust is fine, something else warned" shape), which both makes the fixture realistic and preserves the test's original, still-correct intent ("T1 doesn't touch the generic non-underspec fallback") under the new, stricter §2.4 branch that only fires when `can_fly` is genuinely *not* `True`.

## Behavior changed

- A frame with mass+material already declared but no size class no longer closes the acquisition wizard or degrades a follow-up `"ayúdame a elegir"` to re-asking for mass/material — it now asks for the class in pulgadas, reading persisted state instead of only the current utterance.
- `status_type=="warning"` no longer prints a `"Última simulación: WARNING"` line when Continuity's own `situation` line is already present and honestly says `"fail"`.
- Continuity's autonomy-below next step no longer claims `"el empuje ya es PASS"` when thrust did not actually pass (`can_fly` is not `True`) — it now names both problems (or just the thrust problem, if autonomy isn't the active blocker) without any PASS claim, and never suggests `"ayúdame a elegir"` or names a SKU (deferred to the not-yet-ratified catalog-honesty investigation per the IC's own C-A gate).
- Architecture 4/4 no longer suggests `"puedes optimizar o simular"` while the last simulation is a real failure (any reason, not only autonomy-undemonstrated as the Structure A/N1 hotfix already covered) — the evidence line (`"Arquitectura completa (…)"` / `"Arquitectura 4/4 — completa ✓"`) still shows, since that's evidence, not a next action.
- Nothing else: D8 (`_motor_covers_requirements`, `find_motors_for_requirements` sort), `MotorSuggestion`, `bound_motor_sku_is_underspec`, `_derive_overall`/ERF/`ASSEMBLY_READY`, simulator formulas, `status_type`'s enum values, and `orchestrator.py`'s overall structure are all untouched — confirmed by `git diff` scope (only the 5 files in §5 plus one test-fixture completion) and by the full suite staying green.

No change to the optimize wizard's own routing (`optimizar propulsión` still enters the generic iterate wizard, untouched — out of scope per §4 non-goals). ## Remaining risks / notes for review

- The IC's §2.6 asks only to gate the WARNING line render on `continuity.situation` presence, matching nominal/no_data. I implemented exactly that (not the alternative "retire the WARNING line entirely" the investigation had also floated) — the WARNING line can still appear on its own when Continuity has no `situation` to show (e.g. a fixture with `status_type=="warning"` but no active project-continuity computation reachable), which is the same behavior the nominal/no_data siblings already have. This is a narrower, more conservative fix than "always prefer Continuity," matching the IC's literal instruction.
- `frame_next_missing_question`'s `class_incompatible` wording is new copy not given verbatim by the IC (only the `size_class` sentence was locked in §2.1). I kept it consistent with Structure A's existing `GAP-FRAME-PROP-SIZE` Continuity sentence (LEVEL A, "no verificado", no "cabe"/"no cabe"), but flagging it explicitly since it wasn't handed to me as locked text — worth a look during review.
- The low-completeness frame probe fix (orchestrator.py) builds a `SimpleNamespace` shim rather than a real `model_copy` of `ProjectState`, mirroring the existing pattern already used by `frame_size_blocks_structure_complete` in `project_closure.py` for the same reason (the callers here don't have a full mutated `ProjectState` to construct cheaply) — consistent with prior art in this codebase, not a new pattern.
