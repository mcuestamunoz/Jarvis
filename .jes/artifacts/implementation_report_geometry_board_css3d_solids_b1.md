## Files changed

- `ui/spatial-board/src/scene3dScale.ts` (**new**) — **§3.1**: `SCENE3D = {pxPerMm: 0.5}` (no `maxPx`), `mmToPx(mm, pxPerMm?)` (plain multiplication, never `Math.min`), `solidExtentPx(geometry, pxPerMm?)` — box maps `length_mm→x, width_mm→y, height_mm→z` (a display-axis convention, documented as such, not a CAD frame); disk maps `diameter_mm→x` and `→y`, and `z` is **always literally `0`** — the function has no height input to read for a disk shape in the first place (the DTO carries none), so there's nothing to invent even by construction.
- `ui/spatial-board/src/scene3dLayout.ts` (**new**) — **§3.2**: `layoutSolidsRow(items, gapPx, pxPerMm?)`. Pure, preserves input order, first `originX=0`, each next origin = running cursor advanced by the previous item's `max(extent.x, extent.y)` footprint plus `gapPx` (CSS px, a plain constant — never assembly millimetres). The function's parameter type never includes card `x`/`y`/`mountedOn`/`parent_key` — confirmed by a dedicated test (`U5`) that passes an item with an extra, unused `x: 9999` field and asserts the layout is identical to one without it, proving the helper structurally cannot read it.
- `ui/spatial-board/src/scene3dScale.test.ts` + `ui/spatial-board/src/scene3dLayout.test.ts` (**new**) — U1–U6 verbatim per §4, plus one extra order-preservation test.
- `ui/spatial-board/src/Solid3D.tsx` (**new**) — **§3.3**: box renders a `preserve-3d` wrapper with **exactly six** `.sb-solid__face` divs (front/back/left/right/top/bottom), each a real flat rectangle positioned via `translateZ`/`translateX`/`translateY` + `rotateY`/`rotateX` at halves of the sourced extents — a genuine cuboid, no seventh slab, no invented face. Disk renders **one** `.sb-solid__disk-face` (`border-radius: 50%`, sized `diameter × diameter`px, `rotateX(90deg)` to lie flat in the scene) — no second face, no `translateZ`, no extrusion of any kind. `onMouseDown` calls `event.stopPropagation()` then `onSelect(id)`, so clicking a solid never also starts the scene's drag-rotate. `data-node-id`/`aria-current` mirror `SpatialCard`'s own convention exactly.
- `ui/spatial-board/src/Scene3D.tsx` (**new**) — **§3.4**: filters `nodes` to those with `geometry`, lays them out via `layoutSolidsRow`, and renders them inside its own `.sb-scene3d__world` container with independent `tilt` (`rotateX`/`rotateY`, default `{55, -30}`) and `zoom` (clamped `[0.5, 2]`) state — **not** `useCanvasTransform`, confirmed by grep: this file imports nothing from that hook. Dragging the scene **background** (not a solid — solids call `stopPropagation`) updates `tilt` via mouse deltas; wheel over the pane scales `zoom`, `event.preventDefault()`'d so it never also triggers the 2D board's own wheel-zoom (a different DOM subtree entirely — see below). A plain click on empty background with no drag simply never calls anything selection-related — there is no code path in this file that clears `selectedId`, so "click empty 3D background does not clear selection" holds by the absence of any such call, not by a special-cased guard.
- `ui/spatial-board/src/InfiniteCanvas.tsx` — **§3.4/§3.5**: `Scene3D` is mounted as a **sibling** of `.sb-viewport`, both direct children of `.spatial-board`, confirmed **not** nested inside `.sb-world`. New `show3DOverride: boolean | null` state — `null` means "no explicit user choice," in which case the effective `show3D = show3DOverride ?? hasGeometry` (shown by default iff any live node has `geometry`, matching §3.4's "default: shown if any node has geometry, else hidden"); a manual toggle sets an explicit `boolean` that then persists across re-fetches within the session (never written to `localStorage`). A "Mostrar 3D"/"Ocultar 3D" toolbar button appears only when `hasGeometry` is true. Toolbar hint gains `· 3D: arrastrar vista`, appended only while `show3D` is true. `onSelect`/`selectedId` are passed straight through to `Scene3D` — the exact same values already passed to every `SpatialCard`, confirmed no second selection state was created.
- `ui/spatial-board/src/spatial-board.css` — **§3.4**: `.sb-scene3d` (fixed `260px` pane, `perspective: 900px`, `border-top` separating it from the 2D viewport above), `.sb-scene3d__world` (`transform-style: preserve-3d`), `.sb-solid`/`.sb-solid__face`/`.sb-solid__disk-face` (flat rectangles/circle, semi-transparent fill + border, `box-sizing: border-box` so borders never distort the sourced-mm sizing), `.sb-solid--selected` (border color change only — no layout shift, mirroring `.sb-card--selected`'s own "outline/border-color only" discipline from the prior IC). No forbidden word (pose/ensamblado/cabe/verificado/colocado) appears anywhere in the new CSS, TSX, or toolbar copy — confirmed by grep.

## Behavior changed

- The 5 live demo families with `geometry` (`motors`, `propellers`, `esc`, `battery`, `flight_controller` — re-confirmed live this session via the real projector output against the actual demo project) now additionally render as CSS 3D solids in a new pane below the 2D board. The 9 without (`frame` root, 4 plates, arm, cage, standoff, `sensors`) render **no solid at all** — `Scene3D` filters them out before layout even runs, exactly mirroring `SpatialGlyph`'s own "absence of `geometry` means no glyph" rule for the 2D case.
- **Declared-scale proportionality confirmed**: the propeller (Ø127mm) and the ESC (50×21.6×12mm) are rendered at the same linear `0.5 px/mm` factor with no cap — at this scale the propeller's disk is `63.5px` across and the ESC's longest edge is `25px`, a real, proportionally-correct 2.54:1 ratio that the old capped `GLYPH.maxPx=120` function would have preserved by coincidence at these particular small sizes, but which the new `scene3dScale.ts` guarantees structurally for any future, larger dimension too (verified directly by `U2`: `mmToPx(300, 0.5) = 150`, deliberately **not** `120`).
- Clicking a solid selects the same `selectedId` a 2D card click would — highlighting both the solid (yellow border, `.sb-solid--selected`) and the corresponding 2D card (`.sb-card--selected`, unchanged from the prior IC) simultaneously, since both read the identical state.
- The 2D board — cards, glyphs, edges, drag/resize, pan/zoom, Encajar/100% — is **unchanged in meaning**: confirmed via diff that `SpatialGlyph.tsx`, `constants.ts` (`GLYPH` untouched), `DeclaredMountEdges.tsx`, `mountEdgeGeometry.ts`, `useCanvasTransform.ts`, and `useBoardNodes.ts` were not modified. `InfiniteCanvas.tsx`'s existing 2D wheel-zoom handler is bound to `boardRef` (the `.sb-viewport` element specifically) via `addEventListener`, a completely separate DOM node from `.sb-scene3d`'s own `onWheel` — the two zoom mechanisms cannot cross-trigger.
- No Python file, DTO shape, projector, writer, or catalog seed was touched — confirmed via `git status --short -- src/ tests/ library/`, empty for this cycle. `package.json` has zero diff — confirmed no dependency was added.

## Remaining risk / notes for review

- Per the IC's own done-criteria, an **Engineer Board smoke** (toggle 3D, click the ESC solid → confirm the 2D card outlines, rotate the scene view by dragging its background, confirm plates/cage/standoff/frame/sensors have no solid) is still the recommended acceptance step before closing this item — this report covers code/tests/types/build only.
- `Scene3D`'s tilt-drag sensitivity (`dx * 0.5` / `dy * 0.5` degrees per pixel) and default tilt angle (`55°`/`−30°`) are implementer-chosen presentation constants, not derived from any spec — easy to retune in a follow-up without touching the honesty-relevant `scene3dScale.ts`/`scene3dLayout.ts` modules at all, which is the intended separation of concerns (scale/layout = tested, pure, honesty-bearing; camera feel = presentational, adjustable).
- The `.sb-scene3d` pane has a fixed `260px` height, appended below the 2D viewport in the existing flex column — on a very short browser window this could compress the 2D viewport more than desired; not addressed here since no viewport-sizing complaint or spec exists for this cycle, named for awareness only.
