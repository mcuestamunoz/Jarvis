## 5. Candidate C — G24-B / G24-C (DSE ranking + explore CTA)

**G24-A is closed and unregressed** (§2). This section is strictly the residual after it.

### 5.1 Post-G24-A user journeys, reproduced live (C1) — the key finding

Reproduced the exact G24 precondition (catalog-bound motor, thrust declared) across three goals on `v0.3.1`:

```text
goal=aumentar_payload:      viable=5, catalog_in_viable_positions=[],  catalog_candidates_generated=4
goal=mejorar_estabilidad:   viable=5, catalog_in_viable_positions=[],  catalog_candidates_generated=4
goal=reducir_masa:          viable=5, catalog_in_viable_positions=[],  catalog_candidates_generated=0
```

**For `aumentar_payload` and `mejorar_estabilidad`, Impl C's Strategy 3 correctly generates 4 real catalog candidates — and all 4 are sorted below the top-5 cutoff.** G24-A's apply-by-index has literally no index to offer for these — the row isn't on the list. This is not the same scenario the G24-A IC's own gate test used (that fixture, from a different motor SKU/params shape, does get a catalog candidate into position 5 — also reproduced, confirming G24-A **does** help in that narrower shape). Both shapes are real and reproducible; the "candidate present but not first" shape G24-A fixes is the **less common** of the two in this sampling.

### 5.2 Residual pain, quantified (C2)

The mechanism (`design_explorer.py:638,647`):

```python
viable.sort(key=lambda c: c.score, reverse=True)
...
viable=viable[:MAX_VIABLE],   # MAX_VIABLE = 5 (design_explorer.py:119)
```

is a **single global sort + truncate** — no reservation, no diversity injection. Catalog candidates compete on identical footing with unconstrained abstract deltas (§4.5/B4 of the prior investigation, re-confirmed unchanged: `_score_candidate` has no cost/feasibility term). When ≥5 abstract deltas outscore every real catalog candidate — which the two repro'd goals show is common, not an edge case — **no apply mechanism (index or otherwise) can reach the catalog row**, because it was discarded before the user ever sees the list.

### 5.3 G24-B effort/risk (C3)

A literal `_score_candidate` formula rewrite (adding a cost/feasibility term to prefer catalog rows) is what the prior investigation scoped as "G24-B" — this **does** require reopening the ★6 lock (`_build_label_components`'s docstring: *"`_score_candidate` is unchanged (★6 locks scoring)"*) and its own explicit Engineer ★, per this contract's own hard constraints (§3).

**A narrower, lower-risk alternative exists and is worth surfacing:** a **viable-selection** change — reserve one (or a small fixed number of) slot(s) in the post-sort, pre-truncate list for the best-scoring catalog-native candidate(s), *without* changing `_score_candidate`'s formula or any existing candidate's score. This touches only the ~10-line block at `design_explorer.py:638-647`, never the scoring function itself. It is not literally "G24-B" as the prior finding doc named it (a ranking *tiebreak inside scoring*), but it solves the exact same demonstrated gap (§5.1) with a smaller, more auditable diff. It still changes user-visible explore-list composition, so it still deserves its own explicit Engineer ★ — just not necessarily the same ★6-reopening one a scoring-formula change would need. **Flagged for Engineer choice, not decided here** (★3 in this report's ★ list).

### 5.4 G24-C alone (C4) — NOT sufficient by itself

An honest CTA ("candidate #1 is abstract, will drop your SKU — say 'aplica la N' to keep it") **presupposes a catalog candidate is somewhere in `.viable` to point to**. §5.1 shows that's false roughly as often as it's true in this sampling. A CTA-only fix would, in the common case, have nothing to reference — at best it could honestly say "no catalog-native option ranked among the top 5 for this goal," which is honest but doesn't restore the capability G24-C's own name implies. **G24-C is a real, cheap, worthwhile addition regardless — but not a substitute for §5.3's selection fix.**

### 5.5 Impact on Closure/readiness (C5) — still non-blocker

Unaffected either way — explore/apply visibility has no bearing on `ASSEMBLY_READY` (confirmed repeatedly across three prior arcs; `_bom_sku_resolved`/verdicts never read DSE state).

### 5.6 Relative leverage vs. other candidates (C6)

Of the four candidates, C is the only one where **live, reproducible evidence on the current baseline shows the previously-shipped fix (G24-A) frequently doesn't apply** — not "still has rough edges," but "structurally cannot help" in a demonstrated, common shape. That is a stronger, more concrete "still broken" signal than A (already-shipped, remaining work is research-shaped) or B (no blocker, larger scope) can show, and larger in scope than D (real but narrow display nit).

## 6. Candidate D — Frankenstein `.name`

### 6.1 Reproduced @ v0.3.1 (D1)

Catalog-bound `sunnysky_r2305_2500` → `"optimiza para aumentar payload"` → `"aplica la mejor"` (abstract `#1`, diverges `per_motor_max_thrust_n`/`motor_count`):

```text
name:        sunnysky_r2305_2500           (stale — unchanged)
completeness: high
BOM line:    ✓ motors: sunnysky_r2305_2500 qty=6 (high)
estado line: ✓ motors: sunnysky_r2305_2500 qty=6 (high)
estado line: • Catálogo: candidatos sunnysky_r2305_2500, emax_rs2205_2300
```

### 6.2 Trace (D2)

`sync_motors_component_from_params` (`component_sync.py`) is the function that runs immediately after `invalidate_diverged_catalog_refs` on this path — its own docstring is explicit that it touches **only** `motor_count`/`thrust_n`/`torque_nm`, by design (*"power_w, kv_rating, weight_g, catalog_ref, and every other property are left exactly as they were"*). `.name` staleness is a **documented, deliberate omission**, not an oversight — `invalidate_diverged_catalog_refs` (`catalog_bind.py`) likewise never touches `.name`, only `catalog_ref` and, for battery, `battery_mass_kg`.

### 6.3 Impact (D3)

- **BOM (`format_bom_lines`):** honest at the *identity-claim* level (`sku_resolved=False` → no `[sku]` bracket, confirmed unchanged) but the bare name string is indistinguishable in format from a genuine freeform declaration that happens to read like a SKU — a real, if subtle, misread risk, live-verified above.
- **Readiness/gaps:** unaffected (already established — `classify_component` doesn't inspect `.name` shape).
- **Continuity:** the motor catalog gap surface can suggest the *same string* as a "candidate" while it's simultaneously displayed as the (no-longer-accurate) current motor name — a second, compounding confusion source, observed live in this session's repro (§6.1's last line).

### 6.4 G24-A interaction (D4)

Reduces incidence **only** in the subset of cases where a catalog candidate survives into `.viable` and the user picks it by index instead of applying an abstract `#1` — per §5.1, that subset is not the majority in this sampling. In the common case, G24-A provides no protection against this scenario.

### 6.5 Fix options (D5)

| Option | Effort | Notes |
|---|---|---|
| Clear `.name` to a generic label on divergence (e.g. the component_type or a fixed "motor (declarado)" string) inside `invalidate_diverged_catalog_refs` | Small — one field added to the existing `model_copy(update={"catalog_ref": None, ...})` call already there | Localized to the one function that already owns this exact moment; does not change *when* divergence is detected, only what the resulting spec's `.name` reads |
| `estado`/BOM-only disclaimer (leave `.name`, add a marker when `catalog_ref is None` but `.name` matches a known library SKU string) | Small-Medium | Display-only, touches `format_bom_lines`/`render_startup_context`; requires a live library re-check of `.name` against `has_motor`, a slightly unusual use of the library (name-as-heuristic, not identity) |
| Sync `.name` from params/props on every divergence (broader) | Medium | Would need a defined "what should the name become" rule beyond just clearing it — more design surface than the gap needs |

### 6.6 Micro-IC? (D6)

Yes — the first option (§6.5) is genuinely small: one field addition inside a function that already exists specifically to handle this moment, no G5 semantic change (the *decision* to clear `catalog_ref` is unchanged; only what `.name` becomes afterward changes), no new subsystem, no schema change.

### 6.7 Live blocker (D7)

None — confirmed non-blocking for `ASSEMBLY_READY`/gaps (§6.3). Severity is trust/UX, not correctness or capability.
