## Files changed

### Mass leak fix (§2.1)

- `src/jarvis/domains/aerial.py` — `extract_frame_properties` extended with a `size_class_inch` regex (`5 pulgadas` / `5 in` / `5 inch(es)` / `5"`), deliberately no mm pattern. Docstring updated.
- `src/jarvis/core/iterate_interactive_session.py` — the two confirmed leak points (`_awaiting_material_value` branch and the Gap-1 same-turn strategy-embedded branch) now call `extract_frame_properties` on the full raw text **before** truncating to a bare material name, and carry `mass_kg`/`size_class_inch` forward on `draft.component_patch["frame"]` via a new `_build_frame_patch_from_props` static helper. `_extract_material_from_text` (now fully unused — both call sites shared its exact alias table via `extract_frame_properties`/`resolve_material_alias`) and the now-unused `_KNOWN_MATERIALS` import were removed.
- `src/jarvis/actions/iterate.py` — `_run_declarative_iteration` gained a frame branch (mirroring the existing motors/battery catalog-bound branches): when `component_patch["frame"]` carries `mass_kg` and/or `size_class_inch`, it calls `set_frame_material` and — unlike every other declarative branch — recalculates (`calculation_engine.build` + `simulator.evaluate`), persisting the fresh result into `latest_results` instead of leaving the pre-mass-change stored calc/sim stale. Material-only input (no mass, no size) takes no writer call, unchanged from before.
- `src/jarvis/core/component_writers.py` — `set_frame_material` gained an optional `size_class_inch: float | None = None` parameter. Component-property-only (no `current_parameters` mirror); `None` means "leave whatever is already declared," same convention as `material`.
- `src/jarvis/core/orchestrator.py` — `_apply_inferred_component_spec`'s frame branch now reads `spec.properties.get("size_class_inch")` and passes it through to `set_frame_material` (the acquisition path already benefits from `extract_frame_properties`'s new regex with zero further changes there).

### Class-compatibility screening (§2.2)

- `src/jarvis/core/project_closure.py` — three new pure helpers: `propeller_diameter_in(project_state)` (priority: bound propeller property → `current_parameters["propeller_diameter_in"]` → catalog SKU declaration), `frame_class_compatibility_state(project_state)` (`not_required` / `missing` / `class_compatible` / `class_incompatible`), and `frame_size_blocks_structure_complete(design_properties, params)` — a duck-typed adapter so the two `_block_progress_status` copies (which carry `design_properties`/`params` separately, not a full `project_state`) can share the exact same predicate as the gap builders.
- `src/jarvis/core/orchestrator.py` — `_block_progress_status`'s `"structure"` branch gained an AND-condition via `frame_size_blocks_structure_complete`: components-present is necessary but no longer sufficient. Also `_component_prompt_for_first_missing` now mentions pulgadas for the frame prompt when a propeller diameter is already known (best-effort `_safe_active_project()` lookup; `_COMPONENT_PROMPTS`'s static default is untouched for every other case).
- `src/jarvis/core/engineering_readiness.py` — identical AND-condition in its own `_block_progress_status` copy (kept byte-for-byte in sync with orchestrator's). New `_frame_class_gaps(project_state)` builder emitting `GAP-FRAME-SIZE-MISSING` / `GAP-FRAME-PROP-SIZE` (both MEDIUM, `blocks=["structure"]`, short English titles matching the existing `Gap.title` convention — never the long Spanish CTA), registered in `build_engineering_readiness`'s `gaps +=` sequence. Neither type added to `_INCOMPATIBLE_CLASS_GAP_TYPES` / `_INCOMPATIBLE_VERDICT_SUBSYSTEMS`. `_derive_overall` itself untouched — a MEDIUM gap blocking `"structure"` already forces that subsystem's verdict away from `PASS`, which the existing rollup loop already turns into `NOT_ASSEMBLY_READY` (proved, not just asserted — see the investigation report §5 and the new regression test below).
- `src/jarvis/core/project_continuity.py` — new `_frame_class_next_step(project_state, readiness)` rank carrying the two locked Spanish sentences (LEVEL A / CLASS-BASED, never "cabe"/"verificado"). Gated on `readiness is not None` (every existing caller that omits `readiness` is unaffected — verified via `test_continuity_legacy_path_unchanged_without_readiness`). Positioned right after the BOM `incomplete` rank and before `next_architecture_label`, so the specific message isn't swallowed by the generic "Siguiente bloque: Estructura (en progreso)" line when structure is genuinely the next incomplete architecture block.

## Behavior changed

- Declaring a frame material **and mass** in the same iterate utterance (via the "cambiar material" wizard, either turn shape) now writes `structure_mass_override_kg` and `components["frame"].properties["mass_kg"]` — previously silently dropped to a string-only `design_properties.structure.material` patch (the confirmed walk leak).
- A frame declaring only a material (no mass) is unchanged — no writer call, no invented mass.
- When a propeller diameter is known (bound component, `current_parameters`, or catalog SKU) and the frame declares no `size_class_inch`, the structure architecture block is no longer "complete" and `GAP-FRAME-SIZE-MISSING` (MEDIUM) appears; Continuity names the missing class in Spanish.
- When both are known and `diameter_in > size_class_inch`, structure is likewise not "complete" and `GAP-FRAME-PROP-SIZE` (MEDIUM) appears with a class-incompatibility sentence — never a claim that the propeller physically doesn't fit.
- When `diameter_in <= size_class_inch`, or no propeller diameter is known at all, nothing changes — a mass+material-only frame still completes structure exactly as before.
- Thrust/power/RPM/Ct/autonomy are unaffected in every case — confirmed by a direct `CalculationEngine.build()` identical-output test on the same params with vs without `size_class_inch`.
- Nothing else: G5, DSE apply honest, Block Closure, Option B, T1+2, G22 filters, `resolve_operating_point`, `_derive_overall`'s own code, control/sensors catalogs — all untouched, confirmed by `git status` showing no changes to any forbidden file.

## Remaining risks / notes for review

- `mutation_engine.py`'s `apply_material_definition` was deliberately left unchanged — the IC flagged it as "not the primary leak," and tracing confirmed the real truncation happens one layer up in `iterate_interactive_session.py`. It still writes the legacy `design_properties.structure.material` string field as a side effect (pre-existing, harmless — `components["frame"]` is the canonical read point since Fase 3) whenever a material-shaped DEFINE draft is applied; this is unchanged behavior, not new.
- The frame prompt's pulgadas mention (`_component_prompt_for_first_missing`) does a best-effort `_safe_active_project()` load per call when the first missing key is `"frame"`. This is the same pattern used elsewhere in the file (`_try_start_acquisition_from_mention`, etc.) and is cheap (in-memory tmp-project reload), but it is a new per-call project load at up to 10 call sites that previously did a pure dict lookup — flagging for awareness, not because it changed behavior anywhere it shouldn't.
- Six pre-existing test fixtures needed a compatible `size_class_inch` added (listed above) — all mechanical, none touched the assertions those tests exist to protect. Worth a spot-check that none of them was *silently* supposed to also exercise a missing-frame state that this fix papers over; re-reading each confirmed frame/structure was incidental to all six.
