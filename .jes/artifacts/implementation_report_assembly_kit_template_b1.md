## Deviation from the IC found and fixed during implementation (reported per §1)

The IC's §3.6.4 states: "`_handle_component_description` fallback already `set_control_component` + 'registrado.' Keep it." I verified this **empirically** (live throwaway orchestrator run, before writing any code) and found it is **not sufficient on its own**: `infer_components`/`infer_component` has no `ComponentRule` registered for `power_connector`/`signal_harness` (unlike `flight_controller`/`sensors`, which reach that generic write fallback via a *real* aerial `ComponentRule` that already produces the correct `suggested_key`). Any free-text description of a kit hole (e.g. "XT60 amarillo bullet connector") therefore always comes back as `suggested_key == "generic_component"`, and the existing FN-017 B4 guard in `_handle_component_description` (`"never silently write a generic_component placeholder"`) correctly strips it out of `processable` — the wizard would loop forever, and the kit key would never actually get saved.

Fix (in `orchestrator.py`, same file the IC already lists, mirroring the existing motors/propellers/frame "force" blocks immediately above it): when the single expected key is a kit key (`KIT_HOME_BLOCK` membership — never `BLOCK_TO_COMPONENTS`) and every inferred spec is still `generic_component`, **relabel** (not re-infer — there is no rule to re-infer against) the first non-`"low"`-completeness spec's `suggested_key`/`component_type` to that kit key before the existing `processable` filter runs. A single-word/trivial answer stays `generic_component`/`low` and correctly re-prompts, matching every other wizard's existing behavior for a non-answer. This is a narrow, same-pattern addition, not a new subsystem — verified end-to-end (T4c) that a real free-text description now saves via the exact `set_control_component` + "{Key} registrado." fallback the IC describes.

## Behavior changed

- **Board**: a `dron`/`uav` project with a declared `energy`/`control` block now shows `power_connector`/`signal_harness` as `kind: "slot"` nodes once its 7 architecture keys are declared (they still show alongside architecture slots when those are also missing). A project with no `vehicle_type`, or `vehicle_type` outside `{dron, uav}` (e.g. `robot`), gets **zero** kit slots — confirmed by T0/T6.
- **BOM**: `build_component_bom`'s `missing` list now includes undeclared kit keys for a `dron`/`uav` project. **A 7-key-complete dron project is no longer BOM-complete** — this is the intended product change (§0 lock 6), confirmed live against the demo project (`missing: ['power_connector', 'signal_harness']`, still `vehicle_type: dron`).
- **Continuity**: rank 4 (`elif missing:`) now appends the locked B3 sentence to `next_why` when a kit key is in `missing`, naming exactly the kit keys still missing (never a declared one, never the full registry).
- **IDLE DEFINE**: `"declara el conector"` / `"definir harness"` (etc.) on a project with architecture already complete opens a **single-key** wizard for exactly that kit key (`pending == ["power_connector"]` or `["signal_harness"]`) — never `["battery", "motors"]`, never the composite wizard. Mid-architecture, the phrase reaches FN-014 first (unchanged) and the kit path is not even attempted (kit keys aren't in `BLOCK_TO_COMPONENTS`, so FN-014 itself can't match them — this is structural, not a new guard). A free-text description saved into that wizard writes `set_control_component` with `completeness` whatever the generic inference produced (low/medium), no `catalog_ref`, no `_geometry_from_spec`-relevant keys — confirmed T4c.
- **Architecture / PASS / hover / autonomy**: byte-identical. `_block_progress_status` (both the orchestrator and `engineering_readiness.py` copies) reads `BLOCK_TO_COMPONENTS`/`get_block_type` directly and was not touched — confirmed via `git diff` (empty for both). T1/T5 directly prove a kit-aware state and its no-`vehicle_type` clone produce identical `complete` status on all 4 blocks; T7 proves declaring one kit key doesn't touch `propulsion`'s status.
- **3D / catalog / version**: no `Solid3D`/`scene3dLayout`/`scene3dScale`/`Scene3D` file touched (confirmed, only prior-cycle diffs present); no new catalog SKU family; no `_geometry_from_spec` change; `pyproject.toml` still `0.3.8`.

## Remaining risks / notes for review

- The relabel fix (see "Deviation" above) is the one piece of this implementation not literally spelled out in the IC's own file-by-file plan, though it lives in a file the IC already names (`orchestrator.py`) and follows the exact shape of code already present there. Flagging explicitly for Cursor's review since the IC's own §3.6.4 wording implied this would work with zero additional code.
- `resolve_kit_mention` currently only distinguishes kit keys from everything else via a caller-supplied `kit_keys` list — if a future non-kit `COMPONENT_TERM_ALIASES` entry were ever added with the same string as a kit alias (e.g. someone later added `"conector"` for a different family), the whole-word lookup would still resolve to whichever value the shared dict currently maps that token to (last-write-wins, same as any Python dict) — no new collision risk was introduced here since `"conector"`/`"xt60"`/`"harness"` did not previously exist in `COMPONENT_TERM_ALIASES`, confirmed by reading the table before editing.
