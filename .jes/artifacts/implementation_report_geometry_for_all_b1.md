New `ComponentLibrary._parse_standoffs(name, raw)` static method (mirrors `_parse_plates`): rejects a non-list `standoffs` value, and per the IC's own lock, an **empty** list returns `None` (no child height projection) rather than an empty-but-truthy list. `_frame_from_raw` extended to parse all three new fields.
- `src/jarvis/core/catalog_bind.py` — **§3.3/§3.4**:
  - `bind_frame_from_catalog`: two new `if spec.body_length_mm is not None` / `body_width_mm` blocks, projecting `PropertyValue(unit="mm", source="declared")` onto the frame **root** — placed immediately after the existing `wheelbase_mm`/`configuration` blocks, same pattern, same "never enters `_frame_completeness`" comment repeated (confirmed `_frame_completeness` itself was not touched — still mass+material only).

The standoff call site computes `standoff_height` from `spec.standoffs`: a single entry projects as a bare `float`; two or more project as a `" / "`-joined string in seed order (`"30 / 22"`, `"25 / 32"`) — **never averaged, never truncated to one value**. `count`/`material` scalar projection for standoff is completely unchanged and independent of this new path.

- `tests/test_geometry_for_all_b1.py` (**new**) — 12 tests covering T1–T7: loader parsing for both enriched rows (T1×2), root projection for iFlight body footprint and its absence on TBS-5in (T2×2), standoff height-string projection for TBS (T3) and iFlight (T4), Armattan and TBS-7in-DC left completely untouched (T5×3), body-only and standoff-height-only specs never producing a glyph (T6×2), and a non-regression check that Armattan's pre-existing arm/plate thickness projection is unaffected (T7).

- `default_library.get_frame("tbs_source_one_v5_5in")`/`"iflight_xl7_v4_7in"` now carry the new fields; every other seeded frame (`armattan_rooster_5in`, `tbs_source_one_v5_1_7in_dc`) is unaffected — confirmed via dedicated tests (T5/T5c) and via `git diff` showing no numeric change to either row.
- `bind_frame_from_catalog("iflight_xl7_v4_7in")`'s projected `ComponentSpec` now has `properties["body_length_mm"]`/`["body_width_mm"]` = 202mm each. `frame_part_specs_from_catalog` for both enriched SKUs now includes a `frame_standoff` child carrying a `height_mm` text property (a joined string for both, since both rows have exactly two heights).
- Confirmed **no new glyph** anywhere: `_geometry_from_spec` returns `None` for a frame root with only `body_length_mm`/`body_width_mm` (no height — can't complete a box triple) and for a `frame_standoff` with only `height_mm` (no diameter — can't complete a disk) — both asserted directly (T6) and consistent with every existing thickness-only/material-only part already behaving this way.
- **Live-verified against the real demo project** (`workspace/autonomía-de-10min-9ada1a1b0cca`, dry-run only, not persisted — `git status --short workspace/` is clean): the demo's Armattan-bound frame shows **zero change** — `frame`'s fields/geometry and `frame_standoff`'s `material: "aluminio"`-only fields are byte-identical to before this IC, exactly matching the IC's own §3.6 expectation ("Demo Armattan: no Board change expected from seed alone").

## §3.6 — Refresh / already-bound projects (confirmed, no code needed)

Verified live (not persisted): `refresh_component_from_catalog(state, "frame")` on a project bound to `iflight_xl7_v4_7in` immediately picks up `body_length_mm`/`body_width_mm` on the **root**, since refresh re-runs `bind_frame_from_catalog(sku, base=spec)` exactly as Fase 1's own refresh IC already does for `wheelbase_mm`/`configuration`. Confirmed it does **not** create or touch a `frame_standoff` child at all (`refresh_component_from_catalog` only ever writes `components[component_key]`, a single dict key, by construction — the same "single-key write" property the Fase 1 refresh report already established for frame). Standoff height text therefore only appears via the existing catalog **re-pick/apply** path (`frame_part_specs_from_catalog` + `upsert_frame_part`, the same mechanism that already creates/refreshes plate and arm children on a pick) — no new helper was written or needed, per the IC's own "prefer reuse" instruction. This is the same honest, already-precedented split as ESC mass hygiene's own N4 note: refreshing an already-bound project's **root** is one action; getting new **child** data requires the pick/apply path, not a silent rewrite.

## Remaining risk / notes for review

- The two-value join format (`"30 / 22"`, `"25 / 32"`) is a `str`-typed `PropertyValue.value` — this is consistent with `PropertyValue.value: str | float | int | None`'s existing type, but any future generic code that assumes every `*_mm`-suffixed property is numeric (there is none today, confirmed by grep, but worth naming) would need to handle this string case. `_geometry_from_spec` was checked and does not read `height_mm` at all, so it's unaffected either way.
- Per the IC's own explicit lock (§3.4.4), standoff `count` was **not** auto-summed from the per-height entries (iFlight's `4 + 4 = 8` is recoverable but was left unstated) — each `StandoffSeed.count` is preserved in the seed/schema for fidelity and possible future use, but no aggregate count property is projected onto the Board card today.
